# ADR-0003: RAG Ingestion and Search Method

- Status: Accepted
- Date: 2026-10-04

## Context

仕様では、RAGの引用にページ番号（PDF）またはセクション名（Markdown）を表示し、閾値未満の検索結果しかない場合は回答を生成しないことを求めている。

当初の構成では、取り込みをAzure AI Searchのインデクサーに任せていた。しかし、インデクサー標準の分割（Text Splitスキル）ではページ番号と見出しの情報が失われる。また、検索方式は`open-questions.md`では未決、`roadmap.md`ではベクトル・ハイブリッド検索が将来構想となっており、文書間で矛盾していた。キーワード検索（BM25）のスコアは正規化されないため、固定の閾値による根拠判定にも向かない。

## Decision

- 取り込みは、リポジトリ内のPythonスクリプトで行う。スクリプトは形式ごとに分割し（PDFはページ単位、Markdownは見出し単位）、Azure OpenAIの埋め込みモデルでベクトル化して、AI SearchのPush APIで登録する。
- 検索は、キーワード検索とベクトル検索を組み合わせたハイブリッド検索とし、セマンティックランカーで再順位付けする。
- 根拠の有無は`@search.rerankerScore`（0〜4）の閾値で判定する。

## Alternatives

- インデクサーとDocument Layoutスキル: 自動同期できるが、Document Intelligenceの追加費用と対応リージョンの制約がある。抽出されるメタデータもスキルの仕様に左右される。
- キーワード検索とセマンティックランカー: 埋め込みモデルが不要で構成は単純だが、言い換えや表記ゆれに弱い。
- キーワード検索のみ: 閾値の判定が不安定になる。

## Consequences

ページ番号とセクション名を確実に扱え、分割処理を単体テストできる。文書の追加・更新・削除は、スクリプトを実行するまでインデックスへ反映されない。

Azure OpenAIに埋め込みモデルのデプロイが必要になる。AI Searchは、セマンティックランカーとManaged Identityが使えるBasic以上のSKUが前提になる。文書の自動取り込み（Blob Storageの変更検知）はロードマップへ移す。
